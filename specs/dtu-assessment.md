## Integration Surface Inventory (MANDATORY — all categories required)

Categorized by data flow direction and business criticality. All six categories assessed per DTU methodology.

### Inbound Data Sources (External → Product)

Systems monocle reads from: APIs polled, feeds consumed, webhooks received.

### Outbound Operations (Product → External)

None identified — rationale: monocle is observe-only for workflow state and transcripts. It does not write to external services, send notifications, trigger ticketing, or process payments. Hook POST response bodies are echo/pass-through, not outbound operations to external systems.

### Identity & Access (Bidirectional — auth flow)

| # | Service | Protocol | Fidelity | DTU? | Justification |
|---|---------|----------|----------|------|---------------|
| 1 | Claude Code IDE authorization header | HTTP bearer token | L2 Stateful | NO | Token generated by monocle's own daemon (written to lock file; Claude Code reads). Token generator and validator are the same binary. No external identity provider. Integration test with real lock-file token rotation (SOQ-2 invariant) is sufficient. |

### Persistence & State (Product ↔ Storage)

None identified — rationale: monocle's persistence is entirely local (lock file, config at `~/.monocle/config.json` via `tempfile::persist`, hybrid RAM ring + async JSONL flush for hook events). No external databases, caches, object stores, or message queues. All persistence surfaces are filesystem-local and testable with real FS fixtures.

### Observability & Export (Product → Monitoring)

None identified — rationale: Phase 1 uses `tracing 0.1` with structured fields only; no external log aggregator, metrics platform, or tracing backend is integrated in Phase 1. The event ribbon panel is internal to the TUI. OTel export is a Phase 4 consideration.

### Enrichment & Lookup (External → Product, on-demand)

None identified — rationale: monocle does not call external enrichment services. PID liveness checks are local OS calls. Fuzzy matching (nucleo 0.5) operates on local session state. No external threat intel, geocoding, pricing, or lookup services are integrated.

## DTU Architecture

### Docker Compose Structure

| Clone | Port | Fidelity | Depends On |
|-------|------|----------|-----------|
| dtu-claude-code-hooks-v1 | 8765 (configurable) | L3 Behavioral (>=0.95 vs real Claude Code 2.x payloads) | monocle-daemon lock file (reads port + token) |

**Endpoint matrix the clone synthesizes:**

| Hook type | HTTP method | Path | Auth header | Body fields |
|-----------|-------------|------|-------------|-------------|
| PreToolUse | POST | `/hooks/pre-tool-use` | `X-Claude-Code-Ide-Authorization` | `type, pid, tool_name, tool_input` |
| Notification | POST | `/hooks/notification` | `X-Claude-Code-Ide-Authorization` | `pid, tool_name, tool_input, message` |
| Stop | POST | `/hooks/stop` | `X-Claude-Code-Ide-Authorization` | `pid, stop_reason, session_id` |
| SessionStart | POST | `/hooks/session-start` | `X-Claude-Code-Ide-Authorization` | `pid, session_id` |
| UserPromptSubmit | POST | `/hooks/prompt-submit` | `X-Claude-Code-Ide-Authorization` | `pid, session_id` |

Schema source: canonical 5-endpoint matrix from any-context BC-HOOK-001..BC-HOOK-041 (verified against hooks-r1/r2 ingest rounds). Note: monocle's canonical Phase 1 paths (`/hooks/pre-tool-use` etc.) differ from any-context gene-source paths (`/notify`, `/stop`, etc.). The clone must target monocle's paths.

Fidelity validation: `dtu-validator` agent compares clone payloads against recorded session sample (if available) or schema-derived fixtures from BC-HOOK-007. Update cadence: monthly schema check against public Claude Code docs; quarterly re-validation against fresh recorded session.

## Clone Development Approach

The `dtu-claude-code-hooks-v1` clone is developed as a VSDD story with:

- Behavioral contracts derived from any-context BC-HOOK-001..BC-HOOK-041 (5-endpoint matrix, auth header spec, timeout values, body fields)
- Contract tests verifying clone payloads match the BC-HOOK canonical matrix at field and type level
- Implementation as a lightweight Rust HTTP server (axum) or Python FastAPI server depending on Phase 1 story decomposition test infrastructure decisions
- Docker packaging for portability across CI environments
- Demo recording showing the clone driving monocle's hook ingestion pipeline end-to-end

Clones are scheduled in Wave 1 of the Phase 1 wave schedule to ensure availability before any product story that depends on hook protocol integration testing.

Phase 4 clone candidates: `dtu-rmcp-server-v1` (MCP bridge) and `dtu-russh-server-v1` (federation SSH). Both are out of Phase 1 scope; decision deferred to Phase 4 architecture gate.
